Introduction

Thank you for choosing AutoHub — a business-listing website for auto services, built with Next.js (website, owner dashboard and admin panel), NestJS (API) and PostgreSQL. Everything runs in Docker, so you do not install Node.js or a database yourself.

  • Visitors search garages and auto businesses by category, location and rating, read reviews, send enquiries and chat with owners.
  • Business owners register their listing with photos, then manage bookings, customers, messages and email announcements.
  • You (admin) review new listings, manage users and categories, watch chats, and set the homepage hero images and popup ad.

One installation is one website. The installer asks for a domain, builds the site and gives you a private address where you create your admin account.

Requirements

You needDetails
A VPS with root accessUbuntu 22.04 / 24.04 or Debian 12, 2 GB RAM or more (the first build needs it) and some free disk space. Shared or cPanel hosting will not work.
A domainTwo DNS A records pointing at the server’s IP: app.yoursite.com (the website) and api.yoursite.com (the API). Both names must share one parent domain, because the login cookie needs it.
Free ports80 and 443.
Google Maps keyYour own key (Google Cloud), restricted to your site address. Maps do not work without it.
An email account (SMTP)For password reset and email confirmation. You can add it after installing.
The installer installs Docker for you if it is missing. Images are built on your server, so the first install takes several minutes.

Installation (one command)

  1. Point your domain. Create the two A records above. They can take from a few minutes to a few hours to spread.
  2. Upload and unzip. First unzip the package you downloaded on your own computer: the file to upload is the inner AutoHub.zip. On your computer (PowerShell on Windows, Terminal on Mac or Linux), in the folder that holds it: 
    scp AutoHub.zip root@YOUR_SERVER_IP:/root/
    Then log in to the server, install unzip and unpack the file into /opt. This creates the folder /opt/autohub: 
    ssh root@YOUR_SERVER_IP
apt-get update && apt-get install -y unzip
cd /opt && unzip /root/AutoHub.zip
cd /opt/autohub
    If you log in as a normal user instead of root, put sudo in front of apt-get and unzip. Everything below is run from inside /opt/autohub.
  3. Run the installer: 
    sudo bash install.sh yoursite.com you@email.com
    Run it without arguments and it asks for the domain and your email instead.
  4. Wait. It checks the server, installs Docker if needed, writes .env with fresh random secrets, builds and starts the site, waits until it is healthy and checks the HTTPS addresses.
  5. Copy the setup code printed at the end, together with the address of the web installer. The code is also saved in install-credentials.txt.
The installer is safe to run again. It never replaces an existing .env and never touches the database.
Always start the scripts with sudo bash (for example sudo bash install.sh), not ./install.sh.

Web installer

  1. Open https://app.yoursite.com/install.
  2. Enter the setup code, your name, email and a password (8 to 72 characters, with an uppercase letter and a number).
  3. Submit. Your admin account is created and you can log in.

The page locks itself once an admin exists: the API answers 404 from then on, and the setup code stops working. A wrong code is refused, and after 5 attempts in one minute from the same address you must wait.

The web installer creates only the admin. Email, Google/Facebook login and AI keys stay in .env (see Email (SMTP)).

After installing — checklist

  • Log in at the website with your admin account.
  • Add your categories under Admin → Categories. A new site starts with no listings, and the category filter and the home page categories come from this list.
  • Set up email: sudo bash setup-smtp.sh (next section).
  • Add your Google Maps key to .env as NEXT_PUBLIC_GOOGLE_MAPS_API_KEY, then run sudo docker compose up -d --build frontend.
  • Keep a copy of .env in a safe place. It holds your database password and JWT secret.
  • Schedule the daily backup (see Backup & restore) and copy backups off the server.
Settings starting with NEXT_PUBLIC_ and CSP_MODE are built into the website. After changing one, rebuild with docker compose up -d --build. Other settings only need docker compose up -d.

Email (SMTP)

AutoHub sends password-reset, email-confirmation and contact messages. Run the guided script:

sudo bash setup-smtp.sh

It asks for the mail server, port, user, password and sender, saves them in .env and restarts the API only. The password is typed hidden and never printed. It keeps a copy of .env first (.env.bak-<date>, readable by root only), tests the connection, and prints a clear error if the login fails. Run it again any time; press Enter to keep a saved value. Use --no-restart to apply the change later with docker compose up -d --force-recreate backend.

Gmail: use smtp.gmail.com, port 587, and an app password (Google account → Security → 2-Step Verification → App passwords). Your normal Gmail password does not work.

With REQUIRE_EMAIL_VERIFICATION=true (the default), new users must confirm their email before logging in. Keep SMTP working, or nobody can sign up. The admin created by the web installer is exempt.

Updating

  1. Unzip the new package into a new folder on the server.
  2. Run the script from that folder: 
    sudo bash update.sh

It finds your running AutoHub by itself. If you run several, it stops and lists them; give the path of the one to update: sudo bash update.sh /opt/autohub. It then:

  1. backs up the database and uploaded images (if the backup fails, the update stops);
  2. moves the old program files to previous-version/ and copies the new ones in;
  3. adds any new settings from .env.example to your .env without changing your values (a copy is saved as .env.bak-update-<date>);
  4. checks the configuration (on a problem it puts the old files back), rebuilds, waits up to 5 minutes for the site to be healthy and checks HTTPS.

At the end it offers to delete previous-version/ and the unpacked update folder.

OptionWhat it does
--dry-runShow what would happen; change nothing.
--yesNever ask questions. It does not delete anything by itself.
--cleanDelete the old version and the unpacked update folder after a successful update (skipped if the HTTPS check fails).
--skip-backupSkip the backup. Not recommended.
--no-verifyDo not wait for the HTTPS check.
Your data is kept. The update replaces all program files, but never deletes .env, backups/ or install-credentials.txt. The database and uploaded images live in Docker volumes and are untouched. Deleting .env would make Postgres reject its password and sign everyone out.
If you edited docker-compose.yml or deploy/Caddyfile, the update overwrites them. Your old copy is in previous-version/.

Backup & restore

The installer does not schedule backups, so add the job yourself. Run a backup by hand from the install folder:

sudo bash ops/backup/backup.sh

It saves two files in backups/: the database (autohub-<date>.dmp) and the uploaded images (autohub-uploads-<date>.tar.gz). A failed or empty backup is deleted and reported as an error, so a broken file never looks valid. Backups older than 14 days are removed.

Setting (environment variable)What it does
BACKUP_DIRWhere backups go (default ./backups).
KEEP_DAYSDelete local backups older than this (default 14).
GPG_RECIPIENTEncrypt every file for this GPG key before storing it.
RCLONE_REMOTEAlso copy every file off the server with rclone, e.g. r2:autohub-backups.

Daily at 02:00 — open root’s crontab with sudo crontab -e and add (change the folder to yours):

0 2 * * * cd /opt/autohub && bash ops/backup/backup.sh >> backups/backup.log 2>&1
The backup holds real user data (emails, password hashes, chats). The backups/ folder is readable by root only, so use sudo to list it. Encrypt (GPG_RECIPIENT) any copy that leaves the server. The backup does not contain .env: keep a separate private copy of it.

Check a backup

A backup you have never restored is only a hope. This restores into a throw-away database, prints row counts and deletes it; your live site is not touched:

sudo bash ops/backup/restore.sh verify backups/autohub-YYYYMMDD-HHMMSS.dmp

A good result ends with “OK: the backup restores cleanly”. Do this monthly.

Restore

sudo bash ops/backup/restore.sh restore backups/autohub-YYYYMMDD-HHMMSS.dmp backups/autohub-uploads-YYYYMMDD-HHMMSS.tar.gz

This replaces the live database and, if you give the second file, the uploaded images. Encrypted .gpg files must be decrypted first: gpg --decrypt file.gpg > file.

Restore on a new server

  1. Install AutoHub on the new server (Installation).
  2. Copy the two backup files into its backups/ folder.
  3. Run the restore command above. The database is replaced, so you log in with the accounts from the old server and the web installer is not needed.
  4. If you kept the old .env, the old secrets can be reused; otherwise users simply have to sign in again.

Anyone can list a business: sign up, then open Register your business (/register). The form has five steps: Business Details, Location & Contact (the address is searched and placed on the map), Services Offered, Hours & Amenities and Review & Submit.

A new listing is pending and invisible to visitors until you approve it under Admin → Review.

Chat assistant

Every listing page has a chat button. A visitor asks a question and gets an answer straight away, built from that business's own details. The owner or an admin can step in at any time. It works as soon as the site is installed, with no extra setup.

  • What it answers: booking, services, products and prices, opening hours, address, reviews, contact info and the business's website.
  • General chat (outside a listing, for example on the home page): it can find the closest business when the visitor allows location access, for example "nearest garage to me".
  • Unknown questions get a friendly general reply that lists what it can answer, or an AI answer if you turned that on (below).

Taking over a chat

  1. Owners open Chats in their dashboard (/dashboard/chats); admins open Chats in the admin panel. The list refreshes by itself every 5 seconds while the page is open.
  2. Open a thread and reply. The visitor's chat checks for new messages every 4 seconds and shows your reply.
  3. As soon as a person replies, the assistant stops answering that chat. Either side can end it.

Owners see only chats on their own listings. Admins see every chat.

Optional AI answers

Off by default (AI_PROVIDER=none). To turn it on, set AI_PROVIDER (openai, anthropic or groq) and the matching key in .env, then run sudo docker compose up -d. See Settings reference (.env). The AI is asked only when the built-in rules found no match. If it is off, slow or failing, the visitor gets the normal general reply, so the chat never breaks. Using a provider costs money on your account with it, and the visitor's question is sent to that provider, so mention it in your privacy policy.

Limits and privacy

Starting chats and sending messages are rate-limited per visitor address. Chats are stored in the database, so they are included in backups, and they can hold names and emails.

Security checklist

  • Use a strong admin password (8 to 72 characters, uppercase and a number) and never share it.
  • Keep .env private. It holds the database password and JWT secret. Never email it or put it in git.
  • Keep the server patched (sudo apt update && sudo apt upgrade) and the database port closed to the internet.
  • Schedule backups, test a restore monthly, and encrypt copies that leave the server.
  • Turn on two-factor sign-in for your hosting, domain and email accounts.
  • Review the Audit log after any suspicious report. Monthly, trim it: sudo docker compose exec backend npm run prune-audit-log -- --days=365 --confirm.
  • After a staff change, change JWT_SECRET (everyone is signed out) and any SMTP or API keys they knew.
  • When you are happy with the site, consider CSP_MODE=enforce (see docs/DEPLOYMENT.md).

Built in: passwords hashed with bcrypt; login rate limits and a 15-minute lock after 5 wrong passwords; httpOnly cookies; single-use email links; upload size and content-type checks; security headers (HSTS, frame blocking, CSP); an audit log; and analytics only after cookie consent.

For developers

  • Stack: Next.js, React, TypeScript, Tailwind CSS (frontend); NestJS, Prisma, PostgreSQL, JWT cookie auth, Nodemailer (backend).
  • Containers: db (PostgreSQL 16), backend (port 3001, health check at /health), frontend (port 3000), caddy (HTTPS). Volumes: pgdata, uploads, caddy_data, caddy_config.
  • The backend runs npm run start:prod:migrate: it applies database migrations, then starts.
  • Useful commands (from the install folder): 
    sudo docker compose ps
sudo docker compose logs -f backend
sudo docker compose restart backend
sudo docker compose exec db psql -U autohub -d autohub
  • More notes are in docs/: DEPLOYMENT.md, SECURITY.md and TESTING.md.

FAQ

Can I use shared or cPanel hosting? No. AutoHub needs a VPS with root access and Docker.

Why two domain names? The website and the API run on separate names under one parent domain, so the login cookie works. Use --app-domain and --api-domain for names other than app. and api..

Can I change the domain later? Yes: edit APP_DOMAIN and API_DOMAIN in .env, point DNS at the server, then run sudo docker compose up -d --build.

Where is my data? In Docker volumes (pgdata for the database, uploads for images), not in the program folder.

Can one installation run several sites? No. One installation is one website.
